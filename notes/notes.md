    👉 [QUEUE] Adding to Redis

    It’s: API → Queue → (Worker picks later)


======================== REDIS To RABBITMQ ===============================

# What Redis does well
    Very fast ⚡ (in-memory)
    Very simple
    Push → Pop
# Where Redis falls short
    1. No guarantee of processing
        If worker crashes after popping : Log is gone ❌
    2. No acknowledgment system
        Redis does NOT know : Did worker actually finish the job?
    3. No real “queue system features”
        No retries
        No dead-letter queue
        No routing
        No priorities

# What is RabbitMQ?
    Instead of a bucket, you now have:
        📮 Producers (you)
        📦 Queues
        🧠 Broker (RabbitMQ)
        🧑‍✈️ Consumers (worker)
    Smart routing (advanced)
        RabbitMQ can decide : Which worker should get which log
    Producer → Exchange → Queue → Consumer → ACK

# “I would integrate logging directly into backend services or use log collectors like Fluentd to push logs into RabbitMQ instead of relying on manual ingestion.”

# I built a system where logs don’t directly hit the database.Instead, they go through a queue (RabbitMQ), and a worker processes them asynchronously. This helps in handling high load and improves system reliability.”

# Why RabbitMQ?”
“To decouple services and avoid blocking API requests.
Also added retries and DLQ to handle failures gracefully.”

# What problems did you face?”
“I faced queue configuration mismatch issues where RabbitMQ threw PRECONDITION errors.
That helped me understand that queues are immutable and all services must declare them consistently.”

# What if system is under heavy load?”
“RabbitMQ acts as a buffer, so even if there’s a spike, logs are queued and processed asynchronously without overwhelming the system.”

# What if worker fails?
“I implemented retries and a dead-letter queue. Failed logs are retried, and after a limit, moved to DLQ for later inspection.”
